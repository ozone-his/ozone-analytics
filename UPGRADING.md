# Upgrading to Ozone Analytics 3.0.0

3.0.0 is not a rolling upgrade. The CDC pipeline is **rebuilt**, and both datastores have their
data directories rewritten. Read this end to end before starting, and run it in staging first.

Do the phases in the order given. They are sequenced deliberately:

- MariaDB is upgraded **before** Debezium, because Debezium 3.6 reads MariaDB with a different
  connector than 1.9 used and is only verified against 10.11.
- PostgreSQL is restored **before** Debezium, because restoring drops the `odoo_debezium`
  replication slot -- which the Debezium cutover has to recreate anyway.
- Kafka is rebuilt **before** Debezium, because the reset of Connect offsets and schema history is
  a side effect of starting from an empty broker.

## What survives, and what is rebuilt

| | |
|---|---|
| **Preserved** | OpenMRS and Odoo source databases; the analytics tables; Superset dashboards, charts and users |
| **Rebuilt** | Kafka topics and consumer offsets; Debezium offsets and schema history; Flink state, checkpoints and savepoints |

Nothing authoritative lives in Kafka -- every CDC topic is derived from a source database, so it can
be regenerated by a Debezium snapshot. The analytics tables are written by primary-key upsert, so
reprocessing rewrites the same rows rather than duplicating them.

**Plan for a full re-snapshot.** After the cutover Debezium re-reads every source table and Flink
re-flattens all of it. On a large OpenMRS database this is the longest part of the upgrade and the
analytics tables are incomplete until it finishes. Size the window accordingly.

## Phase 0 -- Back up

Take these before touching anything. Everything below is destructive.

```bash
cd docker

# Source and analytics databases.
docker compose exec mysql \
  mariadb-dump -u root -p"$MYSQL_ROOT_PASSWORD" --all-databases \
  --single-transaction --routines --triggers --events > backup-mariadb.sql

docker compose exec postgresql \
  pg_dumpall -U "$POSTGRES_USER" > backup-postgres.sql
```

Verify both dumps are non-empty and end cleanly (`tail -1` should show a completion comment) before
continuing. Snapshot the Docker volumes as well if your platform supports it.

## Phase 1 -- Stop the stack

```bash
cd docker
docker compose down
```

Leave the volumes in place for now; they are replaced per phase below.

> **On the `docker volume rm` commands below.** They assume the default named volumes, under the
> `ozone-analytics` compose project used by `scripts/start.sh`. If your deployment sets
> `MYSQL_DATADIR`, `POSTGRES_DATADIR` or a different project name, the data lives at that path
> instead -- clear that directory rather than removing a volume. Confirm which applies before you
> delete anything:
>
> ```bash
> docker volume ls | grep ozone-analytics
> grep -E "MYSQL_DATADIR|POSTGRES_DATADIR" .env
> ```

## Phase 2 -- MariaDB 10.3 to 10.11

10.3 has been end-of-life since 2023. Dump and restore is the documented path here: it skips several
major versions at once, which in-place upgrades do not handle reliably.

```bash
cd docker

# 1. Remove the old data directory (the dump from Phase 0 is your copy).
docker volume rm ozone-analytics_mysql-data

# 2. Start MariaDB 10.11 on an empty volume. MARIADB_VERSION is already set in .env.
docker compose -f docker-compose-db.yaml up -d mysql

# 3. Wait for it to accept connections, then restore.
docker compose -f docker-compose-db.yaml exec -T mysql \
  mariadb -u root -p"$MYSQL_ROOT_PASSWORD" < backup-mariadb.sql

# 4. Reconcile the system tables with the new server version.
docker compose -f docker-compose-db.yaml exec mysql \
  mariadb-upgrade -u root -p"$MYSQL_ROOT_PASSWORD"
```

Check afterwards that binary logging is on and row-formatted -- Debezium cannot read the source
without it:

```sql
SHOW VARIABLES LIKE 'log_bin';         -- expect ON
SHOW VARIABLES LIKE 'binlog_format';   -- expect ROW
```

> `utf8` is an alias for the deprecated `utf8mb3` in 10.11, so the server logs a deprecation warning
> for the charset flags in the compose command. It is a warning, not a failure. Migrating the schema
> to `utf8mb4` is worth scheduling separately -- it is a data change, not a version bump.

## Phase 3 -- PostgreSQL 13 to 16

PostgreSQL data directories are major-version specific, so 16 will refuse to start on 13's data.

```bash
cd docker

# 1. Remove the old data directory (the dump from Phase 0 is your copy).
docker volume rm ozone-analytics_postgresql-data

# 2. Start PostgreSQL 16 on an empty volume. POSTGRES_VERSION is already set in .env.
docker compose -f docker-compose-db.yaml up -d postgresql

# 3. Restore. pg_dumpall output includes the CREATE DATABASE and role statements.
docker compose -f docker-compose-db.yaml exec -T postgresql \
  psql -U "$POSTGRES_USER" -d postgres < backup-postgres.sql
```

Confirm the databases came back and that logical replication is still enabled, which the Odoo
connector depends on:

```sql
\l                                  -- expect analytics, superset, hapi, odoo
SHOW wal_level;                     -- expect logical
```

The `odoo_debezium` replication slot is **not** carried over by `pg_dumpall`. That is intended:
Debezium recreates it in Phase 5.

## Phase 4 -- Rebuild Kafka on KRaft

3.0.0 replaces the ZooKeeper-based `debezium/kafka` image with `apache/kafka` in KRaft mode. A KRaft
broker cannot read a ZooKeeper-era data directory, so the volume is replaced rather than migrated.

```bash
cd docker
docker volume rm ozone-analytics_kafka-data
```

This is also what resets Debezium: the Connect offsets (`my_connect_offsets`), configs, statuses and
the schema history topic (`dbhistory.openmrs`) all lived in Kafka. Starting empty clears the 1.9-era
state that the 3.6 connectors cannot read -- stale offsets from the old connector are exactly what
causes a GTID error on first start.

## Phase 5 -- Start, and let Debezium re-snapshot

```bash
cd scripts
./start.sh
```

On start, `connect-setup` registers the rewritten connector definitions from `docker/connect/`. With
no offsets present, both connectors take a fresh snapshot:

- **OpenMRS** -- `snapshot.mode: when_needed` sees no offsets and snapshots every included table.
- **Odoo** -- Debezium recreates the `odoo_debezium` slot and `odoo_publication`, then snapshots.
  The database user needs privileges to create both.

Watch progress:

```bash
# Connector state -- both should reach RUNNING, with no FAILED tasks.
curl -s http://localhost:8383/connectors?expand=status | jq

# Topics filling up.
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
```

## Phase 6 -- Verify

1. **Connectors healthy** -- both `RUNNING`, no failed tasks (command above).
2. **Flink jobs running** -- the Flink UI on `:8085` shows **one job per flattening statement**
   (~12), all `RUNNING`. 3.0.0 submits each statement as its own job; a single combined job means
   an old image is still deployed.
3. **No pending jobs** -- if some jobs sit in `SCHEDULED`, the cluster is short of slots. Total
   slots (`numberOfTaskSlots` x `TASK_MANAGER_REPLICAS`) must be at least
   *number of statements* x `parallelism.default`. See `docker/flink/config/config.yaml`.
4. **JobManager stable** -- it should not be restarting. A JobManager restart loop with
   `OutOfMemoryError: Metaspace` in its logs means `jobmanager.memory.jvm-metaspace.size` is too
   small for the number of jobs.
5. **Data landing** -- row counts climbing in the analytics tables:

   ```bash
   docker compose exec postgresql \
     psql -U analytics -d analytics -c \
     "select relname, n_live_tup from pg_stat_user_tables order by relname;"
   ```

6. **Temporal columns readable** -- spot-check a flattened row against its source. Debezium 3.6
   emits dates and timestamps as formatted strings natively, which is why the TimestampConverter SMT
   was removed. Values should match the source, not appear as epoch numbers.

## Rolling back

There is no in-place rollback once the volumes are replaced. To return to the previous release:
restore the Phase 0 dumps into the old image versions, redeploy the previous distro, and let the old
Debezium connectors re-snapshot. This is why Phase 0 is not optional.

## Notes on what changed

| Component | 2.x | 3.0.0 |
|---|---|---|
| Apache Flink | 1.17.1, embedded MiniCluster | 2.3.0, standalone cluster (application mode) |
| Job topology | one job for all flattening statements | one job per statement |
| Kafka | `debezium/kafka` + ZooKeeper | `apache/kafka` 4.3.1, KRaft |
| Debezium | 1.9 (Docker Hub) | 3.6.0.Final (quay.io) |
| OpenMRS connector | `MySqlConnector` | `MariaDbConnector` |
| Connector config | `database.server.name`, `database.history.*` | `topic.prefix`, `schema.history.internal.*` |
| Temporal columns | TimestampConverter SMT + jar | native Debezium 3.x string output |
| Kafka/Connect UI | Kowl | Redpanda Console |
| MariaDB | 10.3 | 10.11 |
| PostgreSQL | 13 | 16 |
